# Цифровой учёт в цеху: что сделано и что дальше

Файл для того, кто продолжает работу (человека или новый чат с Claude).
Исходного документа владельца («Цифровой учёт в цеху», 2 окт 2026) в
репозитории нет, его суть пересказана ниже.

## 1. Зачем всё это (из документа владельца)

Сейчас рабочему, чтобы отметиться в Битрикс24, нужно пять действий, а пользы
ему никакой. Решение: отметка — одно действие, и она привязана к деньгам
(не отметил — не заработал).

- У каждого рабочего личный бейдж со штрихкодом (заламинированная карточка).
- На титульном листе заказа печатается QR с номером сделки (`DG-1234`).
- На каждом участке планшет или старый ПК со сканером. Сканер работает как
  клавиатура: «печатает» код и жмёт Enter.
- **Подошёл к станку:** пикнул бейдж → пикнул титульник → «Начал».
- **Закончил:** пикнул титульник → одна из трёх больших кнопок:
  - «Готово»;
  - «Готово с замечанием» → причина (скол, ошибка в УП, брак плиты);
  - «Проблема» → уведомление Алексею (мастер) в Битрикс.
- Экран участка сам показывает очередь: заказы, дошедшие до участка, по дате
  отгрузки. Утром берёшь верхний.
- После отметки рабочий сразу видит заработок: «Сегодня 2 140 ₽ · за месяц 41 300 ₽».
- Сделка: объёмы берутся из товаров сделки (п.м. распила, м кромки, отверстия,
  листы упаковки) × ставка «операция → ₽ за единицу». Двое на заказе — поровну.
- Брак: ОТК при приёмке жмёт «Брак» и выбирает участок; система знает, кто его
  делал. Не оплачивать переделку или вычитать — решает владелец (настройка).
- Когда рабочий жмёт «Готово», сделка сама переходит на следующую стадию
  Битрикса. Участки, которых нет в заказе (например, без присадки), пропускаются.
- Сервер стоит в цеху; без интернета цех продолжает отмечаться, в Битрикс всё
  уйдёт, когда связь вернётся.
- Порядок внедрения: табло → пилот на присадке → остальные участки → месяц
  «теневого режима» (считаем, но платим по-старому).

### Устройство `shop/` (Python 3.10+, только stdlib, SQLite)

- `server.py` — HTTP-сервер, маршруты через декоратор `@route`, страницы из
  `shop/web/`. Запуск: `python shop/server.py` (порт 8080) или
  `python shop/server.py --demo` (поддельный Битрикс, база `shop/data/demo.db`
  пересоздаётся при каждом запуске).
- `logic.py` — все правила: поиск по скану, объёмы, маршрут по участкам,
  сессии, оплата, брак, отчёт. **Логика терминала уже написана и покрыта
  тестами**, этапу 3 нужен в основном интерфейс.
- `sync.py` — фоновый поток: отправить очередь `outbox` в Битрикс, забрать
  сделки и товары. `syncer.wake()` — отправить сразу.
- `db.py` — схема; транзакции только через `with db.tx(conn):`.
- `demo.py` — `FakeBitrix` и `seed()` (участки, ставки, люди, 15 сделок).
- `web/common.css`, `web/common.js` — токены темы и помощники: `$`, `esc`,
  `fmt`, `rub`, `api(path, body)`, `toast(msg, "err")`, `shortTs`, `shortDate`.
- Тесты: `python -m unittest discover -s shop/tests` (сейчас 38, все зелёные).

Правила, уже реализованные в `logic.py`:

- Сессия — заход на участок по заказу. Второй бейдж на открытую сессию —
  присоединение (двое — деньги поровну).
- «Готово»:
  - начисление = объём операции × ставка, ставка сохраняется на момент закрытия;
  - сделка двигается на стадию следующего применимого участка или на финальную
    стадию, только вперёд;
  - комментарий уходит в таймлайн Битрикса.
- Повторное «Готово» тем же участком по тому же заказу — 0 ₽ с пометкой.
- «Проблема»: стадия не меняется, оплаты нет, у сделки ставится пометка
  `problem`, уведомление уходит `im.notify.system.add` пользователю из настроек.
  Следующий «Начал» снимает пометку.
- Брак (`report_defect`): сделка возвращается на стадию виноватого участка.
  - Переделка по вине рабочего — 0 ₽; политика `deduct` ещё и снимает исходное
    начисление.
  - Не вина рабочего — переделка оплачивается.
  - После переделки сделка возвращается туда, откуда её вернули (на ОТК).
- Раскладка: если на планшете русская раскладка и сканер прислал `ВП-1234` или
  `Ц-0001`, сервер сам переводит это в латиницу. Терминал шлёт код как есть.

## 3. Этап 3 — терминал участка (сделано)

Ниже — исходный план этапа, он же описание того, как терминал устроен. Что
добавилось при реализации:

- `/api/terminal/<id>`: у `section` есть `stage_id`, у `sections` — `kind`,
  плюс `today` — дата сервера (срочность в очереди считается по ней: часы
  планшета могут врать).
- `/api/scan`: у `deal` есть `volumes` — объёмы операций этого участка.
- `logic.report_defect` закрывает открытую приёмку ОТК по заказу с
  `result = 'defect'`: без оплаты и без смены стадии. После переделки ОТК
  начинает приёмку заново и получает оплату один раз.
- На ОТК «Брак» есть и на карточке заказа без открытой приёмки — брак видно
  сразу при осмотре. В `reported_by` уходят имена пикнутых бейджей или «ОТК».
- Тап по заказу в очереди или в «Сейчас в работе» — то же, что пикнуть его
  титульник (если титульник потерялся).
- После «Начал», «Готово» и «Брака» бейджи сбрасываются: каждая отметка —
  отдельная цепочка пиков. Без действий 60 с — сброс бейджей и заказа.
- Фокус: тап по кнопкам не забирает фокус у поля кода, а символы, набранные
  при фокусе на кнопке, всё равно попадают в поле кода.
- `common.css`: токены срочности как на табло (`--late-*`, `--soon-*`) и
  цвет текста на заливках (`--on-accent`, `--on-ok`) для тёмной темы.
- Проверка 3.4 пройдена: тесты и сценарии в Playwright (скриншоты 1280 и
  390 в обеих темах, без ошибок в консоли и без горизонтальной прокрутки
  от 360 px).

### 3.1. API, которое уже есть (без PIN, только локальная сеть)

Ошибки приходят как HTTP 400 `{"error": "текст по-русски"}` — их показывать как есть.

`GET /api/info` → `{sections: [{id, name, kind}], addresses: [...], connected, demo}`

`GET /api/terminal/<section_id>` →
```
{ section: {id, name, kind},            // kind: "regular" | "otk"
  sections: [{id, name}],               // все участки по порядку
  queue: [deal...],                     // сделки на стадии этого участка, по дате отгрузки
  open: [{session_id, deal_id, number, client, title, started_at, rework, workers: [имена]}],
  reasons: {remark: [...], problem: [...], defect: [...]},
  shadow: true|false,                   // теневой режим — подписать суммы «не к выплате»
  sync: {at, ok_at, error, pending} }
deal = {id, number, title, client, shipDate: "YYYY-MM-DD"|null, stageId,
        working: [имена], problem: "причина"|"", rework: bool, volumes: ["Распил: 64 п.м.", ...]}
```

`POST /api/scan {section_id, code}` — один из ответов:
```
{type: "worker", worker: {id, name}, today, month}
{type: "deal", deal: {...deal, stageName, gone},
 open_session: null | {session_id, started_at, rework, workers: [имена], worker_ids: [id]},
 rework_here: bool,                     // по сделке на этом участке открыт брак — будет переделка
 passed: [{id, name, at}]}              // участки, уже сделавшие заказ (для «Брака» на ОТК)
{type: "unknown", code}
```
(отключённый бейдж — 400 с текстом)

`POST /api/start {section_id, deal_id, worker_ids: [..]}` →
`{session_id, joined, rework, workers: [имена], deal: "DG-…", section}`

`POST /api/finish {session_id, result: "done"|"remark"|"problem", reason, comment}` →
`{result, deal, earnings: [{worker_id, name, amount, today, month}], warnings: [...], next_stage, note, shadow}`
(`reason` обязателен для `remark` и `problem`; повторное закрытие — 400 «Эта работа уже закрыта»)

`POST /api/defect {deal_id, section_id /*виноватый участок*/, reason, worker_fault: bool, reported_by}` →
`{defect_id, workers: [имена], deducted, policy}`

### 3.2. `shop/web/terminal.html` — поведение

Маршрут `/terminal` уже есть, файла нет.

1. **Привязка к участку.** `/terminal?section=<id>` запоминается в `localStorage`
   (`dg_terminal_section`). Без параметра и без сохранённого — экран выбора
   участка из `/api/info`. В углу мелкая ссылка «сменить участок».
2. **Ввод сканера.**
   - Поле кода всегда в фокусе: возвращать фокус после кликов и закрытия
     окон, кроме поля комментария.
   - Код отправляется по Enter или Tab.
   - `inputmode="none"`, чтобы на планшете не вылезала экранная клавиатура.
     Кнопка «⌨ ввести вручную» переключает на `text`.
3. **Ожидание.**
   - Крупно: название участка и подсказка «Пикните бейдж».
   - Блок «Сейчас в работе» (`open`).
   - Очередь (`queue`) с цветами как на табло: красный — отгрузка сегодня или
     просрочена, жёлтый — завтра; метки «⚠ проблема», «переделка», объёмы участка.
   - Обновлять `/api/terminal/<id>` раз в ~15 с.
   - Внизу мелко: статус связи с Битриксом (`sync.ok_at`, `pending`). Это не
     ошибка цеха — работа идёт и без Битрикса.
4. **Бейдж** (`type: worker`) → чип с именем, можно пикнуть ещё один (двое на
   заказе), у чипа крестик. Сброс через ~60 с без действий.
5. **Титульник** (`type: deal`):
   - **Есть открытая сессия на этом участке:**
     - бейджей нет или все уже в сессии → экран окончания с тремя большими
       кнопками;
     - пикнут новый человек → большая «Присоединиться» (`/api/start` с его
       id), рядом те же кнопки окончания.
   - **Сессии нет:**
     - бейджи есть → карточка заказа и огромная кнопка **«Начал»**;
     - бейджей нет → запомнить заказ и попросить «Пикните бейдж», после
       бейджа показать «Начал».
   - **Предупреждения на карточке (не блокировать):**
     - заказ стоит не на стадии этого участка (`deal.stageId` ≠ стадия
       участка; `stageName` для текста);
     - `gone` — закрыт или ушёл из воронки;
     - `rework_here` — будет переделка.
6. **Окончание:**
   - «Готово»;
   - «Готово с замечанием» → крупные кнопки причин из `reasons.remark`;
   - «Проблема» → причины из `reasons.problem` + необязательный комментарий.
   - Пока идёт запрос, кнопки выключены: двойной тап не должен закрыть дважды.
7. **Результат.**
   - По каждому из `earnings`: «Солех: +1 070 ₽ · сегодня 2 140 ₽ · за месяц
     41 300 ₽».
   - Если `note` — показать её (переделка, повтор). Если `shadow` — подпись
     «теневой режим — не к выплате».
   - `next_stage` — «заказ ушёл на: Кромка».
   - `warnings` — жёлтой плашкой (нет объёмов — сообщить Алексею).
   - Через ~10 с назад в ожидание; тап — сразу назад.
8. **ОТК** (`section.kind === "otk"`): на экране окончания четвёртая кнопка
   **«Брак»**:
   1. участок — из `passed`; если пусто, все участки, кроме ОТК;
   2. причина — `reasons.defect`;
   3. «Вина рабочего» / «Не вина рабочего (плита, УП)»;
   4. подтверждение → `/api/defect` → «Делали: …, политика: …».
9. Интерфейс для цеха:
   - кнопки не меньше 64 px, крупный шрифт, читается с вытянутой руки;
   - тёмная и светлая тема через токены `common.css`;
   - короткий звук через WebAudio на успех и ошибку (сканеру нужен отклик);
   - ширина от 360 px без горизонтальной прокрутки.

## 4. Этап 4 — отчёт по сделке: что сделать

Из документа владельца: «Конец месяца. Отчёт в Excel по каждому сотруднику:
заказы, объёмы, сумма, вычеты. Алексей правит спорные строки до закрытия
месяца». Схема оплаты — «оклад + сделка»: работа без заказа (уборка, наладка,
криволинейка) в сделку не попадает. Первый месяц — теневой режим: система
считает, платят по-старому и сравнивают. Ещё нужна статистика брака по каждому
человеку — по присадке её сейчас как раз не хватает.

**Бэкенд отчёта уже написан и покрыт тестами** (`logic.month_report`,
`adjust_line`, `manual_line`, `close_month`, `reopen_month`,
`server.report_xlsx`, `TestReport`). Этапу 4 нужен экран `shop/web/report.html`
и несколько доработок из 4.3.

### 4.1. API, которое уже есть (всё под PIN)

`api()` из `common.js` сам спрашивает PIN при 401 и кладёт его в
`sessionStorage`. Ошибки — HTTP 400 `{"error": "текст по-русски"}`, показывать
как есть.

`GET /api/report?month=YYYY-MM` (без `month` — текущий) →
```
{ month, closed: bool, closed_at: "YYYY-MM-DD HH:MM:SS"|"", shadow: bool,
  people: [{worker_id, name, salary, piece, defect, adjust, total, deals, defects}],
  lines: [line...],
  defects: [{id, deal_id, deal_number, section_id, section, session_id, reason, worker_fault: 0|1,
             policy: "unpaid"|"deduct"|"paid", return_stage_id, reported_at, reported_by,
             resolved_at|null, workers: "Имя, Имя"|null}],
  defects_by_section: {"Упаковка": 2, ...},
  workers: [{id, name}] }                 // работающие — для «Ручной строки»

line = {id, month, worker_id, worker, kind, session_id, deal_id, deal_number, client,
        section_id, section, operation_id, operation, qty, unit, rate, share, amount,
        note, ref_id, created_at, partners: [имена напарников], adjusted: сумма правок этой строки}
```

- `kind`:
  - `piece` — сделка;
  - `defect` — вычет за брак (сумма < 0, `ref_id` — снятая строка);
  - `adjust` — правка (разница, `ref_id` — исправленная строка);
  - `manual` — ручное начисление или удержание.
- `people`: работающие плюс уволенные, у кого есть строки в месяце.
  - `salary` — оклад: в закрытом месяце снимок на момент закрытия, иначе
    текущий из справочника;
  - `piece` — сделка, `defect` — вычеты (≤ 0), `adjust` — правки + ручные;
  - `total = salary + piece + defect + adjust`;
  - `deals` — заказов со сделкой, `defects` — браков по вине рабочего.
- `share` — доля при работе вдвоём (0,5). `qty` — полный объём заказа,
  `amount` — уже доля человека.

`POST /api/report/adjust {ledger_id, amount, note}`:
- `amount` — **новая сумма строки**, а не разница. Сервер сам допишет строку
  `adjust` с разницей и `ref_id`, исходная строка не меняется.
- `note` обязателен.
- Нельзя для строк `adjust` и в закрытом месяце (400).

`POST /api/report/manual {month, worker_id, amount, note}` — ручное начисление
(премия, наладка); удержание — с минусом. В закрытом месяце 400.

`POST /api/report/close {month}`:
- закрыть можно только прошедший месяц;
- оклады фиксируются;
- правки и ручные строки дальше запрещены.

`POST /api/report/reopen {month}` — открыть заново.

`GET /api/report/xlsx?month=` → файл `sdelka_YYYY-MM.xlsx`:
- листы «Свод», «Строки», «Брак»;
- в теневом режиме на «Своде» пометка «ТЕНЕВОЙ РЕЖИМ, не к выплате».

PIN идёт заголовком, поэтому обычная ссылка не сработает. Скачивать так:
`const r = await api(path, undefined, true); const blob = await r.blob();`
→ `URL.createObjectURL` → `<a download>`.

### 4.3. Доработки бэкенда

- **Матрица брака.** В `logic.month_report` добавить
  `defect_matrix: [{worker_id, worker, section_id, section, count}]`.
  - SQL: `defect_workers` ⨝ `defects` (`worker_fault = 1`, месяц по
    `reported_at`) ⨝ `sections` ⨝ `workers`.
  - На клиенте не резать строку имён `defects[].workers` — в имени может быть
    запятая.
- **Список месяцев.** `GET /api/report/months` (под PIN) → `[{month, closed}]`.
  - Месяцы из `ledger.month`, `months.month` и текущий, по убыванию.
- **Снимок теневого режима.** Сейчас `shadow` в отчёте — текущая настройка.
  Выключат теневой режим в ноябре — октябрь перестанет быть помечен.
  - При `close_month` сохранять `months.shadow`; закрытый месяц берёт её,
    открытый — текущую настройку.
  - **Подвох:** база в цеху уже создана, а `CREATE TABLE IF NOT EXISTS` не
    добавит колонку в существующую таблицу. В `db.init` нужна миграция:
    `PRAGMA table_info(months)` → если нет `shadow`, то
    `ALTER TABLE months ADD COLUMN shadow INTEGER NOT NULL DEFAULT 0`.
- **Демо-история прошлого месяца.** Закрыть можно только прошедший месяц,
  поэтому в `--demo` без истории «Закрыть» не проверить.
  - Добавить в `demo.py` функцию (например, `seed_history(conn)`) и вызывать её
    в `server.main` только в демо, после `demo.seed`.
  - Прямые вставки за прошлый месяц: 4–6 выдуманных закрытых заказов в
    `deals` (`gone = 1`), `sessions` + `session_workers`, `ledger` (суммы =
    объём × ставка ÷ число людей, ставки из `demo.seed`), один брак с
    переделкой (0 ₽), одна ручная строка.
  - Не через `finish_session`: он кладёт в outbox смену стадий сделок, которых
    нет в поддельном Битриксе, и в справочниках повиснут ошибки отправки.
- **Ссылки:**
  - на главной (`web/index.html`) карточка «Отчёт по сделке» → `/report`;
  - в навигации `admin.html` пункт «Отчёт»;
  - в README убрать «Отчёт по сделке — следующий этап».

## 5. Соглашения репозитория

- Интерфейс, комментарии и сообщения коммитов — по-русски.
- JS ванильный, без сборки и CDN: всё должно работать офлайн в сети цеха.
- Python — только стандартная библиотека.
- Вебхук Битрикса никогда не отдаётся в браузер (только маска) и не
  коммитится.
- `docs/` публикуется на GitHub Pages — туда только калькулятор и табло.
- Схема БД: в цеху уже есть рабочая база. Новая таблица —
  `CREATE TABLE IF NOT EXISTS` в `SCHEMA`; новая колонка в существующей
  таблице — только миграцией в `db.init` (`PRAGMA table_info` →
  `ALTER TABLE … ADD COLUMN`).
- Деньги в базе не правятся задним числом: начисления, вычеты, правки —
  отдельные строки `ledger` со ссылкой `ref_id`.
